전체 표시 원고

S01 · 도구를 쓰는 AI, 무엇을 기록해야 할까?

AI가 데이터베이스를 조회하고 계산기를 호출하면 그럴듯한 답을 만들 수 있습니다. 하지만 그 답이 어디서 왔고, 어떤 도구가 어떤 입력으로 실행됐는지 모르면 실패를 설명하기 어렵습니다. 오늘은 답 뒤의 과정을 남깁니다.

도구 호출은 모델의 판단, 실행 요청, 도구의 반환, 결과 해석과 최종 출력으로 나뉩니다. 각 단계가 성공했는지는 서로 다른 질문입니다. 모든 단계를 하나의 성공 표시로 합치지 않는 것이 출발점입니다.

실제 ToolUniverse와 MCP 표준 입출력 연결로 작은 과학 도구를 실행하겠습니다. 유료 모델은 호출하지 않고, 로컬 데이터를 읽는 결정적 클라이언트로 흐름을 확인합니다. 모델 능력보다 실행 구조를 배우는 예제입니다.

S02 · 모델의 도구 선택과 도구 실행은 다르다

모델은 도구 이름과 인자를 제안할 수 있습니다. 실제로 실행할지, 인자가 형식에 맞는지, 실행 범위와 시간 제한을 어떻게 둘지는 호스트 프로그램이 처리합니다. 모델이 쓴 글 자체가 실행 결과는 아닙니다.

도구가 값을 돌려주면 모델이나 후속 프로그램이 그 값을 해석합니다. 반환이 정상이어도 대상 분자가 틀리거나 단위가 잘못되면 최종 답이 틀릴 수 있습니다. 호출 성공과 과학적 근거의 정확성을 분리합니다.

오늘의 클라이언트는 미리 정한 호출 순서를 사용합니다. 따라서 ToolUniverse를 연결했다는 사실은 실제로 확인하지만, LLM이 적절한 도구를 골랐다고 평가하지 않습니다. 실습에서 자동화한 부분을 명확히 표시합니다.

S03 · 입력 스키마가 도구의 계약이다

도구 이름만 알면 실행할 수 있는 것은 아닙니다. 어떤 인자가 필요한지, 숫자인지 문자열인지, 허용하는 단위가 무엇인지 정해야 합니다. 이를 입력 스키마로 표현합니다. 형식 계약이 있어야 실수를 빨리 찾습니다.

이번 단위 변환 도구는 양수인 값과 단위를 받습니다. 단위는 나노몰러, 마이크로몰러, 몰러 중 하나입니다. 이름을 비슷하게 쓴 임의의 문자열을 조용히 받아 계산하지 않습니다.

필수 인자가 빠졌거나 값이 음수이면 정상적인 친화도 계산으로 넘어가지 않습니다. 스키마 검증과 도구 내부의 의미 검증을 함께 둡니다. 형식에 맞는 값이라고 연구 대상까지 맞는 것은 아니라는 점도 기억합니다.

S04 · MCP는 연결 규약이다

MCP는 모델을 포함한 클라이언트와 도구 서버가 기능을 발견하고 호출 결과를 주고받는 규약입니다. 시작할 때 연결을 초기화하고, 서버가 제공하는 도구 목록과 입력 스키마를 읽을 수 있습니다.

이 규약 자체가 단백질이나 화합물 데이터를 만들어 주지는 않습니다. 과학 도구는 서버 뒤의 구현에서 실행됩니다. 모델, MCP 연결, 도구 라이브러리와 실제 데이터 서비스를 서로 다른 층으로 생각하세요.

클라이언트가 도구를 호출하면 서버는 결과나 오류를 반환합니다. 반환 내용을 신뢰할지와 기권할지는 그 다음 단계입니다. 잘 연결되는 것과 잘 판단하는 것을 따로 측정해야 하는 이유입니다.

S05 · ToolUniverse를 도구 실행 엔진으로 연결한다

ToolUniverse는 과학 도구를 등록하고 일정한 호출 형식으로 실행하는 라이브러리입니다. MCP 서버와 연결해 도구 이름과 스키마를 클라이언트에 보여줄 수 있습니다. 문서와 실제 설치 버전을 함께 확인합니다.

이번 실습에서는 전체 도구를 한꺼번에 열지 않고 개인 학습 도구 3개만 등록했습니다. 데이터 레코드 읽기, 친화도 단위 변환, 분자 표준 문자열 계산입니다. 모두 프로젝트의 가상환경에서 실행합니다.

과학 도구 목록이 많다고 답의 품질이 자동으로 좋아지는 것은 아닙니다. 필요한 입력과 출력 의미를 이해하고, 실제로 무엇이 호출되었는지 로그로 확인해야 합니다. 다음 장면에서는 이 세 도구의 역할을 나눕니다.

S06 · 작은 과학 도구 세 개의 역할

레코드 도구는 행 번호로 로컬 DAVIS의 공급된 측정값을 읽습니다. 분자와 타겟 식별자, 구조 문자열, 단위와 출처 해시를 함께 반환합니다. 단순히 친화도 숫자 하나만 돌려주지 않습니다.

변환 도구는 값과 명시된 단위를 받아 몰러와 나노몰러, pKd를 계산합니다. 분자 도구는 RDKit으로 canonical isomeric SMILES와 원자 수를 반환합니다. 실제 구현이 담당하는 계산과 데이터 조회를 구분합니다.

이 데이터는 캐시된 실제 공급 레코드이며, 이번 실행에서 ChEMBL이나 UniProt의 온라인 조회를 했다고 표시하지 않습니다. 외부 서비스를 연결할 때도 같은 계약과 출처 기록을 유지할 수 있습니다.

S07 · 표준 입출력의 두 통로를 구분한다

이번 MCP 연결은 표준 입출력으로 통신합니다. 클라이언트가 서버 프로세스를 실행하고 메시지를 주고받습니다. 통신용 표준 출력에 일반적인 설명 글을 섞으면 메시지 파싱이 깨질 수 있습니다.

실행 로그와 진단 문장은 표준 에러나 별도 파일로 남깁니다. 서버가 실제 계산을 끝냈어도 프로토콜 메시지를 읽지 못하면 클라이언트는 실패할 수 있습니다. 데이터의 내용과 통신 상태를 나눠 봅니다.

실습에는 서버의 진단 파일과 클라이언트의 원시 호출 기록이 따로 있습니다. 문제가 생기면 어느 통로에 어떤 출력이 있었는지 확인할 수 있습니다. 이런 작은 분리가 재현과 디버깅을 훨씬 쉽게 합니다.

S08 · 호출 로그에는 연결할 식별자가 필요하다

질문 식별자와 호출 식별자를 각 기록에 붙입니다. 질문 하나가 여러 도구를 부를 수 있으므로, 같은 질문의 실행을 연결하면서도 개별 도구 호출을 구분할 수 있어야 합니다.

도구 이름과 원래 인자, 반환 내용, 시작 시각과 지연 시간을 함께 기록합니다. 잘못된 단위나 식별자를 나중에 발견했을 때, 최종 답만 봐서는 어느 호출에서 섞였는지 알기 어렵습니다.

원시 반환은 그대로 보존하고 읽기 쉬운 요약은 별도 필드에 둡니다. 요약 과정에서 잘못된 값을 고쳐 쓰면 원래 실패의 증거가 사라집니다. 입력과 출력의 연결을 기록하는 것이 감사의 기본입니다.

S09 · 실제 호출: 9개 성공과 입력 오류 1개

세 질문에 도구 세 개씩을 호출해 정상 호출은 모두 9건이었습니다. 별도로 잘못된 입력 한 건을 실행했습니다. 정상 아홉 건과 오류 한 건, 총 10건의 원시 호출 기록을 보관했습니다.

이 수치는 미리 쓴 예시 로그가 아니라 실제 SDK와 SMCP 서버의 호출에서 얻은 기록입니다. 도구 목록과 스키마도 연결된 서버에서 받았습니다. 지연 시간은 호출별로 저장했으며 상황에 따라 달라질 수 있습니다.

성공한 도구 호출의 개수를 LLM 정답률로 읽지 않습니다. 클라이언트의 순서는 우리가 고정했고, 도구는 로컬 데이터를 계산했습니다. 여기서 확인한 것은 연결, 입력 검증과 기록의 흐름입니다.

S10 · 반환 플래그가 전부를 말하지 않았다

실제 설치 버전에서 음수 입력의 오류는 반환된 JSON 안에 상태 오류로 들어 있었습니다. 그런데 MCP 바깥쪽의 isError 플래그는 거짓이었습니다. 플래그 하나만 확인한 클라이언트는 이를 성공으로 셀 수 있습니다.

그래서 실습 코드는 프로토콜 수준의 오류 표시와 도구 본문 안의 의미적 오류를 모두 확인합니다. 원래 반환은 고치지 않고, 후속 상태 분류를 별도 필드에 남깁니다. 실패를 발견한 이유도 추적할 수 있습니다.

모든 MCP 서버가 같은 형태라는 일반 규칙으로 확대하지 않습니다. 이번 ToolUniverse와 SMCP 버전에서 실제로 본 사례입니다. 사용한 버전과 반환 구조를 고정하고, 새 버전에서는 다시 확인해야 합니다.

S11 · 도구 오류는 음성 정답이 아니다

값을 계산하지 못했다고 결합하지 않는다고 답하면 안 됩니다. 오류는 정보가 없거나 실행이 실패한 상태이지, 생물학적 음성 근거가 아닙니다. 최종 스키마에서 판단과 실행 상태를 별도로 둡니다.

판단은 양성, 음성 또는 기권이 될 수 있습니다. 실행 상태는 정상 종료, 입력 오류, 시간 초과와 파싱 실패처럼 나눕니다. 근거와 기권 이유가 있으면 다른 사람이 후속 행동을 정할 수 있습니다.

오류를 조용히 빈 문자열로 바꾸거나 기본 숫자 영으로 채우지 않습니다. 이런 처리 때문에 시스템이 자신 있게 틀린 답을 만들 수 있습니다. 실패는 다음 단계가 처리할 수 있는 명시적 상태로 전달합니다.

S12 · 최종 출력 스키마를 먼저 고정한다

최종 답에는 질문 식별자, 판단, 기권 이유와 사용한 근거의 식별자를 둘 수 있습니다. 자신감 수치를 받는다면 무엇의 확률인지 정의해야 합니다. 형식이 맞는지와 정답인지는 따로 채점합니다.

숫자를 주지 않는 실행기에는 임의의 confidence를 만들어 넣지 않습니다. 이번 결정적 도구 클라이언트도 모델 신뢰도를 출력하지 않았습니다. 없는 값은 값 없음으로 두고, 계산할 수 없는 지표는 표시합니다.

실습용 출력과 공식 프로젝트가 확정할 평가 스키마는 구분합니다. 여기서는 추적과 실패 처리를 배우기 위한 초안입니다. 실제 모델을 연결할 때는 스키마와 파싱 실패 처리 규칙을 먼저 고정해야 합니다.

S13 · 실패 재시도에는 경계가 필요하다

일시적인 연결 실패는 다시 요청하면 해결될 수 있습니다. 하지만 호출이 실제로 실행됐는지 모르는 상태에서 다시 요청하면 비용이나 쓰기 작업이 중복될 수 있습니다. 재시도 규칙은 도구의 성격에 맞게 정합니다.

읽기 전용 캐시 조회와 외부 작업 생성은 다릅니다. 요청 식별자와 결과 영수증을 남기고, 이미 받은 결과를 다시 사용할 수 있는지 확인합니다. 횟수와 시간 제한도 명시해야 무한한 호출을 막을 수 있습니다.

이번 학습 도구는 로컬 읽기와 계산만 수행합니다. 그래도 원시 호출을 남기는 습관은 동일합니다. 나중에 모델 API나 외부 서비스를 붙일 때는 중복 실행 여부와 실제 비용 기록이 더 중요해집니다.

S14 · 외부 DB를 붙이면 출처도 늘어난다

PubMed 문헌 검색이나 ChEMBL과 UniProt 조회를 연결할 수 있습니다. 이때 데이터베이스의 이름만 남기지 않고, 사용한 질의, 엔트리, 가져온 시각과 응답을 보관해야 합니다. 데이터는 시간이 지나면 달라질 수 있습니다.

같은 화합물 이름이 다른 구조를 가리키거나 같은 단백질 이름이 다른 변이를 뜻할 수 있습니다. 원래 질문의 대상을 확인하고, 검색 결과와 측정 레코드를 연결하는 검증 단계가 필요합니다.

이번 영상은 외부 조회가 이미 전부 완성됐다고 주장하지 않습니다. 로컬 도구에서 배운 스키마와 로그 구조를 다음 외부 연결에 적용하는 방법을 설명합니다. 실제 서비스마다 인증과 반환 의미를 확인하고 필요한 부분부터 연결합니다.

S15 · 지연·토큰·비용은 분리해서 기록한다

전체 실행 시간에는 모델이 생각하는 시간과 도구 응답을 기다리는 시간이 함께 들어갈 수 있습니다. 호출별 지연을 남기면 병목이 어느 단계인지 읽을 수 있습니다. 평균뿐 아니라 실패와 느린 사례도 확인합니다.

모델을 호출할 때는 입력과 출력 토큰, 모델 이름과 실제 비용을 기록합니다. 캐시 사용과 재시도 비용을 구분해야 같은 예산의 시스템을 비교할 수 있습니다. 가격표로 추정한 비용과 청구된 비용도 구분합니다.

이번 실습은 유료 모델을 호출하지 않았으므로 모델 API 비용을 사용했다고 표시하지 않습니다. 단위 계산의 지연이 LLM 추론 속도를 대표하지도 않습니다. 무엇을 측정했는지 각 열의 의미를 명확히 유지합니다.

S16 · 작은 실습: 숫자 하나를 호출까지 추적한다

호출 기록에서 질문 하나를 고르고 원래 인자를 읽어 보세요. 어느 도구가 어떤 행을 조회했는지, 측정 단위와 식별자가 원래 질문과 같은지 확인합니다. 반환의 출처 해시를 따라 원본 파일도 찾을 수 있습니다.

변환 도구의 결과와 레코드의 pKd를 계산기로 대조해 보세요. 숫자가 일치해도 대상 분자가 다른 경우를 생각합니다. 계산의 일관성과 과학적 대상의 일치가 별도 검증이라는 점을 기록합니다.

관찰 노트에는 호출 식별자, 사용한 인자, 반환 상태, 발견한 차이와 후속 행동을 적습니다. 스크립트가 끝났다는 것만으로 도구 호출이나 연구 판단을 이해했다고 표시하지 않습니다.

S17 · 로그를 읽으면 실패 가설이 생긴다

답이 틀렸을 때 도구가 선택되지 않았는지, 인자가 잘못됐는지, 데이터가 달랐는지, 결과 해석이 틀렸는지 나눌 수 있습니다. 로그가 없으면 이런 가설을 실제 근거로 확인할 수 없습니다.

실행 기록에는 민감한 키나 필요 없는 개인정보를 그대로 공개하지 않습니다. 연구에 필요한 입력과 출처를 남기되, 인증 정보는 별도로 관리합니다. 재현 가능한 로그와 공개 가능한 로그의 범위를 정합니다.

다음 교란 하네스에서는 도구 반환의 특정 부분만 바꿔 실패를 유도합니다. 지금 만든 호출 구조와 원시 로그가 그대로 필요합니다. 실패를 관찰할 수 있게 만드는 것이 에이전트 연구의 중요한 준비입니다.

S18 · 핵심 요약: 연결과 판단을 따로 검증한다

도구 호출은 모델 제안, 호스트 실행, 반환과 해석으로 나뉩니다. 입력 스키마와 최종 출력 스키마를 고정하고, 질문과 호출 식별자로 원시 기록을 연결합니다. 숫자 하나만 저장하지 마세요.

실제 SMCP 예제에서 정상 호출 아홉 개와 입력 오류 하나를 기록했습니다. 외부 오류 플래그만 보지 않고 본문의 오류 상태도 확인해야 했습니다. 버전과 실제 응답을 확인하는 습관이 중요합니다.

ToolUniverse와 MCP를 연결했다는 사실이 LLM의 연구 판단 성능을 증명하지는 않습니다. 이번에 확인한 실행 구조를 실제 모델, 조회 도구와 교란 실험에 연결하고 각각의 성공과 실패를 따로 평가합니다.

S19 · 문서와 실행 버전을 함께 남긴다

연결과 메시지의 설명은 MCP 공식 문서, 도구 실행은 ToolUniverse 공식 문서를 참고했습니다. 실제 설치된 패키지의 인터페이스도 대조했습니다. 클라이언트와 서버 코드는 개인 실습 폴더에서 확인할 수 있습니다.

로그에는 설치 버전, 제공된 도구 스키마와 원래 반환을 보관했습니다. 라이브 데이터베이스와 유료 LLM을 호출한 것처럼 표현하지 않습니다. 확인한 부분과 다음 연결 단계가 필요한 부분을 가이드에 구분했습니다.

이제 큐레이션 편에서는 질문과 정답, 대상과 난이도 좌표를 정리합니다. 도구가 가져온 정보가 평가할 질문과 맞는지 확인할 기준을 만드는 과정입니다. 실행 구조와 데이터 구조를 함께 준비해 보겠습니다.
